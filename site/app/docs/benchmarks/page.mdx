# Benchmarks

Performance is a design goal, so it is measured and compared against the most widely deployed implementations: FFmpeg's codecs, libopus and x264. This page explains what was measured, how, and what the numbers do and do not show. The short version: on this machine every Ragdoll codec measured here is at least level with its reference, and most are faster.

<Callout title="One machine, one harness">
The codec numbers below come from a single machine and were measured like for like: both libraries called in-process, on the same inputs, with the same number of threads. Treat them as evidence of direction, not as a general claim, and run them on your own hardware before relying on them.
</Callout>

## Codecs against their references

| | |
| :-- | :-- |
| **Hardware** | x86_64 Xeon with AVX2 at 2.1 GHz, 4 vCPUs, in a shared virtual machine |
| **Ragdoll** | `main` at the time of writing, `cargo build --release`, AVX2 dispatch |
| **References** | libavcodec 6.1.1 (FFmpeg's H.264, AAC, Opus and FLAC codecs), libopus 1.3.1 (fixed point) and 1.4 (float), and x264, linked and called directly |
| **Method** | In-process, timing codec calls only (no container parsing, file I/O or process start-up). One thread unless a row says otherwise. Audio: best of several runs. H.264 decoding: the median of 11 rounds that alternate the two decoders, each round the best of three |
| **Noise** | About ±5–10% from session to session; ratios within that band are a tie |

A ratio above 1.00× means Ragdoll is faster.

| Workload | Ragdoll | Reference | Ratio |
| :-- | --: | --: | --: |
| H.264 decode, 1080p x264 High / CABAC, 4 threads | 545 fps | 461 fps (FFmpeg, 4 frame threads) | 1.18× |
| H.264 decode, 1080p x264 High / CABAC, 1 thread | 162 fps | 169 fps | 0.96× |
| H.264 decode, 720p Baseline / CAVLC, 4 threads | 1306 fps | 1349 fps (FFmpeg, 4 frame threads) | 0.97× |
| H.264 decode, 720p Baseline / CAVLC, 1 thread | 666 fps | 711 fps | 0.94× |
| H.264 encode, 720p, QP 26, 150 frames | 366 fps | 342 fps (x264 `ultrafast`) | 1.07× |
| AAC-LC decode, 128 kbit/s stereo | 2510× real time | 1802× (FFmpeg `aac`) | 1.39× |
| AAC-LC encode, 128 kbit/s stereo | 174× real time | 51× (FFmpeg `aac`) | 3.4× |
| Opus decode, 96 kbit/s stereo (CELT) | 529× real time | 460× (FFmpeg `opus`) | 1.15× |
| Opus decode, 16 kbit/s mono speech (SILK) | 1546× real time | 1085× (FFmpeg `opus`) | 1.42× |
| Opus decode, restricted low delay | 547× real time | 362× (libopus 1.4 float) | 1.51× |
| Opus encode, restricted low delay, complexity 9 | 192× real time | 121× (libopus 1.4 float) | 1.58× |
| FLAC decode, 16-bit stereo | 1193× real time | 920× (FFmpeg) | 1.29× |
| FLAC encode, 16-bit stereo | 2778× real time | 475× (FFmpeg, level 5) | 5.9× |

### What the numbers mean

- **H.264 decoding is level with FFmpeg on one thread and ahead of it with four.** The single-thread ratios moved between 0.94× and 1.07× across measuring sessions on this machine, so call them a tie. With four frame threads Ragdoll is ahead on the 1080p High stream and level on the 720p Baseline one. Output is bit-exact with the JM reference decoder and FFmpeg, and identical whatever the thread count.
- **H.264 encoding is compared at matched settings.** At QP 26 Ragdoll's files are the size of x264 `ultrafast`'s, with higher PSNR, and it encodes slightly faster. x264's slower presets still compress better: `veryfast` makes files about a quarter smaller at similar quality, at a fifth of the speed (77 fps), and `medium` runs at 32 fps:

  | 720p, QP 26 | Size | PSNR (average) |
  | :-- | --: | --: |
  | Ragdoll | 2.83 MB | 46.13 dB |
  | x264 `ultrafast` | 2.85 MB | 45.47 dB |
  | x264 `veryfast` | 2.10 MB | 45.86 dB |
  | x264 `medium` | 2.29 MB | 48.25 dB |

- **AAC-LC** decodes within the ISO/IEC 14496-26 conformance tolerance of FFmpeg's float decoder. The encoder holds its target bitrate (within 5% from 32 to 320 kbit/s on the test signals) and produces files the size of FFmpeg's at 128 kbit/s; its quality has been compared by SNR only, not with a perceptual model.
- **Opus** decodes sample-exactly with libopus. In restricted-low-delay mode the encoder is byte-identical with libopus.
- **FLAC** encodes files about 21% smaller than FFmpeg's level 5 on this input, and decoding includes checking each file's MD5 signature, which FFmpeg skips.

## What `ragdoll bench` measures

[`ragdoll bench`](/docs/cli/bench/) times twelve end-to-end workloads on synthesized inputs (probing, remuxing, 4K scaling, FLAC, thumbnails, quality metrics, H.264 transcoding, cutting, audio processing, tone mapping, packaging and a memory-bounded transcode). Each workload runs in-process, and the suite reports wall-clock time and throughput twice: in performance mode, and again in efficiency [power mode](/docs/power/). It is a quick way to see how Ragdoll behaves on your machine and to catch regressions between builds. A run on the machine above, trimmed:

```text
Workload                                        P-Core (ms)    P-Core Rate E-Core (ms) FFmpeg (ms) Speedup(P) Speedup(E)
----------------------------------------------------------------------------------------------------------------------------------
1. Container Probe & GOP Index (300f 4K MP4)        0.07 ms 15188.50 files/s     0.05 ms         N/A        N/A        N/A
2. Zero-Copy Remux (MP4 -> MKV 16 MB 4K)            7.54 ms     2.09 GB/s      7.17 ms         N/A        N/A        N/A
3. 4K -> 1080p Lanczos-3 Scaling (30 frames)      218.78 ms   137.12 fps     287.50 ms         N/A        N/A        N/A
4. Lossless FLAC Encode+Decode (30s 48kHz 2ch)     80.36 ms   373.32 x RT     75.87 ms         N/A        N/A        N/A
...
7. 1080p H.264 Inter Transcode (60f Y4M->MP4)     739.84 ms    81.10 fps    1574.48 ms         N/A        N/A        N/A
...
12. Bounded-Mem (64 MiB) High-CRF Transcode       486.47 ms   123.34 fps     498.70 ms         N/A        N/A        N/A
```

Read these columns with care:

- **The `E-Core` column** only moves work onto efficiency cores on macOS, where Ragdoll sets a background QoS class. Elsewhere, efficiency mode uses fewer threads, and the P-core / E-core split in the header is an estimate (half the logical cores each).
- **The FFmpeg column is not like-for-like.** With `--compare-ffmpeg`, the suite runs the `ffmpeg` and `ffprobe` on your `PATH` as child processes, so each FFmpeg time includes process start-up, probing and file I/O, while each Ragdoll time is an in-process library call. On workloads that take milliseconds, FFmpeg's start-up dominates, and the speedups it prints say more about that than about either codec. The FFmpeg version shown in its output is a fixed label, not the version that ran. Use the codec table above for comparisons.
- **The hardware table is not a measurement.** The second table, of instructions, cycles, power and energy, reads no performance counters on Linux (instructions and cycles print as 0), and its energy figures are CPU time multiplied by fixed per-core constants on every platform. Do not quote them as energy use.

## Kernels

[`ragdoll self-test`](/docs/cli/self-test/) runs every SIMD kernel against its scalar reference on the same input, checks that the results match exactly, and prints the throughput of both. It measures how much each kernel gains from SIMD on your machine; it does not compare against FFmpeg. A run on the machine above, trimmed:

```text
Kernel (4K 3840x2160 Luma / 16 MB Stream)      Scalar         NEON SIMD      Speedup   Check
----------------------------------------------------------------------------------------------
4K Plane SAD (sum |a - b|)                      7.36 Gpx/s      12.18 Gpx/s    1.66x    EXACT (49183200)
4K Plane SSE (sum (a - b)^2)                    1.90 Gpx/s      10.96 Gpx/s    5.76x    EXACT (6295449600)
4K Plane SSIM 4x4-Reuse (vf_ssim)               1.97 Gpx/s       4.88 Gpx/s    2.48x    EXACT (0.93131 / 11.63 dB)
Annex-B Start-Code Scan (isolated 0x00s)        3.00 GB/s       14.72 GB/s     4.90x    EXACT
H.264/HEVC RBSP Unescape (vextq_u8 pair)        0.90 GB/s        3.82 GB/s     4.22x    EXACT
1080p YUV420p -> RGB24 (BT.709 vst3q_u8)        0.18 Gpx/s       0.26 Gpx/s    1.45x    EXACT
...
```

The column is labelled `NEON SIMD` on every architecture; on `x86_64` it is the AVX2 path where one exists, and the scalar reference where it does not, which is why some rows show no gain. `RAGDOLL_SIMD=scalar|neon|avx2` forces a dispatch level.

## Reproduce

```sh
git clone https://github.com/oddurs/ragdoll.git && cd ragdoll
cargo build --release

# Kernel correctness and SIMD gain on this machine.
./target/release/ragdoll self-test

# End-to-end workloads, Ragdoll only, as JSON.
./target/release/ragdoll bench --json > bench.json
```

The codec comparison above links FFmpeg's libraries into a separate harness that is not yet part of the repository; until it is, treat those figures as reported rather than reproducible.

If your results differ meaningfully, or you find a regression between versions, please [open an issue](https://github.com/oddurs/ragdoll/issues) with the `bench --json` output, `ragdoll --version` (it prints the SIMD level and core count), your CPU model and operating system, and whether the machine was otherwise idle.
