# Benchmarks

Performance is a design goal, so it is measured continuously and compared against the most widely deployed implementation, FFmpeg. This page explains what was measured, how, and what the numbers do and do not show.

<Callout title="One machine, one harness">
All numbers below come from a single Apple M4 (4 performance and 6 efficiency cores) and the project's own harness. Treat them as evidence of direction, not as a general claim. Run them on your own hardware before relying on them.
</Callout>

## Setup

| | |
| :-- | :-- |
| **Hardware** | Apple M4, 4 P-cores + 6 E-cores, macOS |
| **Ragdoll** | `v0.1.0`, `cargo build --release` (fat LTO, one codegen unit, `opt-level = 3`) |
| **FFmpeg** | 9.0.2, built with `clang -O3 -mcpu=native` |
| **Inputs** | Synthesized: 64-byte-aligned 3840×2160 planes, 16 MB bitstreams, procedural video and audio from [`synth`](/docs/cli/synth/) |
| **Correctness** | Every Ragdoll kernel result is checked bit for bit against its scalar reference in the same run |

## Kernels

Single-threaded throughput of individual kernels on identical inputs.

| Kernel | FFmpeg 9.0.2 | Ragdoll | Ratio | Why |
| :-- | --: | --: | --: | :-- |
| Annex-B start-code scan, 16 MB | 7.21 GB/s | 32.61 GB/s | 4.52× | FFmpeg's `aarch64` path uses 64-bit SWAR and drops to bytewise scanning at each zero. Ragdoll stays in NEON across isolated zeros. |
| CRC-32 (MPEG-2) | 0.59 GB/s | 2.56 GB/s | 4.34× | Slicing-by-8 tables, eight independent lookups per word. |
| 4K → 1080p Lanczos-3 scale | 214.8 fps | 506.5 fps | 2.36× | Q6 `i16` intermediates in an 8-row L1 ring, 16 pixels per iteration, zero taps skipped. |
| H.264 RBSP unescape | 5.14 GB/s | 10.65 GB/s | 2.07× | Copies 16 bytes at a time and re-enters NEON after each `00 00 03`. |
| 4K plane SSIM | 5.04 Gpx/s | 10.06 Gpx/s | 2.00× | FFmpeg's `vf_ssim` has x86 assembly but no `aarch64` path. |
| H.264 4×4 DCT + IDCT | 125.5 Mblk/s | 191.0 Mblk/s | 1.52× | In-register transpose and single-instruction rounding shift. |
| 1080p RGB24 → YUV420p (BT.709) | 4.03 Gpx/s | 6.02 Gpx/s | 1.49× | Chroma averaging fused into the luma pass; no intermediate rows in memory. |
| 4K plane SAD | 32.11 Gpx/s | 47.87 Gpx/s | 1.49× | Four independent accumulators per row. |
| 4K plane SSE | 14.27 Gpx/s | 22.65 Gpx/s | 1.59× | As above. |
| 8-tap polyphase horizontal scale | 3.17 Gpx/s | 3.78 Gpx/s | 1.19× | 8 pixels per iteration with pairwise reduction. |

**Provenance.** The Ragdoll column is reproducible with [`ragdoll self-test`](/docs/cli/self-test/), which prints these kernels' throughput on your machine. The FFmpeg column was measured during the reference audits recorded in cairn items `SIMD-0024`, `SIMD-0027` and `SIMD-0029`. The harness that drove FFmpeg's internal kernels is not yet in the repository, so that column cannot currently be reproduced from a clean checkout. Bringing it in-tree is tracked as `BENCH-0056`.

## End-to-end workloads

Whole-command comparisons from [`ragdoll bench --compare-ffmpeg`](/docs/cli/bench/). These you can reproduce.

| Workload | FFmpeg 9.0.2 | Ragdoll, P-cores | Ratio | Ragdoll, E-cores only |
| :-- | --: | --: | --: | --: |
| 1. Probe and GOP index, 300-frame 4K MP4 | 30.54 ms | 0.05 ms | — | 0.13 ms |
| 2. Remux MP4 → MKV, 16 MB | 36.41 ms | 15.98 ms | 2.28× | 46.65 ms |
| 3. 4K → 1080p Lanczos-3, 30 frames | 90.80 ms | 17.37 ms | 5.23× | 105.92 ms |
| 4. FLAC encode + decode, 30 s stereo | 110.71 ms | 25.42 ms | 4.30× | 101.82 ms |
| 5. 4×4 contact sheet, 16 thumbnails | 28.26 ms | 3.93 ms | 7.00× | 18.34 ms |
| 6. 4K PSNR + SSIM, 20 frames | 168.92 ms | 7.70 ms | 21.9× | 25.15 ms |
| 7. 1080p H.264 transcode, 60 frames | 232.98 ms | 46.81 ms | — | 187.86 ms |

### Reading these numbers honestly

- **Process start-up is included for FFmpeg and not for Ragdoll.** Ragdoll's workloads run in-process inside `bench`. FFmpeg's run as child processes, so each timing includes exec, dynamic linking and initialization, typically several milliseconds. For workloads that take tens of milliseconds, that is a large share.
- **Workload 1 is not a fair ratio.** `ffprobe -show_packets -of json` serializes every packet as JSON, while Ragdoll builds its index in memory. The roughly 600× gap is mostly process start-up and output formatting, so no ratio is given.
- **Workload 7 is not like-for-like.** FFmpeg runs libx264, a mature encoder that spends its time on rate-distortion decisions. Ragdoll's Constrained Baseline encoder makes far fewer decisions and produces much larger files. Until M7 lands, this row measures pipeline overhead, not encoder quality per second.
- **Workload 6 compares different work.** FFmpeg's `psnr,ssim` filters run through the filter graph with format negotiation. Ragdoll computes the same metrics directly on decoded planes.
- **E-core numbers** show the cost of [efficiency mode](/docs/power/). Restricted to efficiency cores, Ragdoll is slower than FFmpeg on performance cores for remux and scaling, and faster on the other workloads, at an estimated fraction of the energy.

A fairer comparison, with in-process FFmpeg library calls, matched output sizes and quality, and more realistic inputs, is planned as the 12-workload v1.0 suite (`BENCH-0051`).

## Reproduce

```sh
git clone https://github.com/oddurs/ragdoll.git && cd ragdoll

# Kernel throughput and correctness on this machine.
cargo run --release -- self-test

# End-to-end workloads, Ragdoll only.
cargo run --release -- bench

# End-to-end workloads against the ffmpeg and ffprobe on your PATH.
cargo run --release -- bench --compare-ffmpeg --json > results.json
```

If your results differ meaningfully, please [open an issue](https://github.com/oddurs/ragdoll/issues) with the JSON output, `ragdoll --version`, and `ffmpeg -version`.
