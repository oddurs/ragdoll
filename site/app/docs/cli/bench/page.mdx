# ragdoll bench

Run the end-to-end benchmark suite. `bench` synthesizes its own inputs in a temporary directory, runs twelve workloads through Ragdoll's library calls in both performance and efficiency [power modes](/docs/power/), and prints the wall time and throughput of each. It is a quick smoke test of a build's speed on your machine, not a fair comparison with FFmpeg; for like-for-like codec numbers see [Benchmarks](/docs/benchmarks/).

```sh
ragdoll bench [--compare-ffmpeg] [--json]
```

## Options

| Option | Description |
| :-- | :-- |
| `--compare-ffmpeg`, `-c` | Also run an `ffmpeg` / `ffprobe` command for each workload and print the time ratio. Requires both on your `PATH`. |
| `--json`, `-j` | Emit the results as JSON. |

## Workloads

| # | Workload | Ragdoll | FFmpeg command run with `--compare-ffmpeg` |
| :-- | :-- | :-- | :-- |
| 1 | Container probe and GOP index of a 300-packet 4K MP4 (50 runs) | `probe` | `ffprobe -show_streams -show_packets -of json` |
| 2 | Remux, MP4 → MKV, 16 MB (5 runs) | `remux` | `ffmpeg -c copy` |
| 3 | 4K → 1080p Lanczos-3 scaling of 30 frames already in memory | scaler | `ffmpeg -vf scale=1920:1080:flags=lanczos -f null -` |
| 4 | Lossless FLAC encode and decode, 30 s 48 kHz stereo, in memory | FLAC encoder and decoder | `ffmpeg -c:a flac`, then decode back to WAV |
| 5 | 4×4 contact sheet, 16 thumbnails, 640×360 source | `extract --thumbnails` | `ffmpeg -vf scale=160:90:flags=lanczos,tile=4x4` |
| 6 | 4K PSNR + SSIM, 20 frames | `metrics` | `ffmpeg -lavfi psnr;ssim -f null -` |
| 7 | 1080p H.264 encode, 60 frames, Y4M → MP4 | `transcode` | `ffmpeg -c:v libx264 -preset ultrafast -qp 24` |
| 8 | Frame-accurate trim of a 6 s 360p clip | `cut` | `ffmpeg -ss 0.25 -to 5.75` re-encoding with `libx264 -preset ultrafast` |
| 9 | Resample 44.1 → 48 kHz, R128 normalize to −14 LUFS, AAC, 10 s | resampler, loudness meter, AAC encoder | `ffmpeg -af aresample=48000,loudnorm=I=-14:TP=-1.0 -c:a aac` |
| 10 | HDR10 → SDR tone-map plus watermark overlay, 30 frames in memory | tone-map and overlay kernels | `ffmpeg -filter_complex ...tonemap=hable...overlay=16:16` |
| 11 | Three-rendition CMAF HLS + DASH ladder | `package` | three `ffmpeg -f hls -hls_segment_type fmp4` encodes with `libx264 -preset ultrafast` |
| 12 | High-profile CRF encode, 60 frames 720p, 64 MiB budget | streaming GOP encoder | `ffmpeg -c:v libx264 -preset ultrafast -crf 23 -maxrate 4000k -bufsize 8000k` |

Several Ragdoll workloads time a library call on data already in memory, while every FFmpeg command decodes its input from a file, and several of the FFmpeg commands do different work (x264 `ultrafast` against Ragdoll's encoder, a different tone-mapping curve, a full re-encode for the trim, FFmpeg's own HLS muxer). Treat their times as context rather than a race.

## What is measured, and what is not

- **Wall time and a workload rate** (files/s, GB/s, fps, × real time) for each Ragdoll workload, once with the performance profile (`P-Core`) and once with the efficiency profile (`E-Core`). These are the numbers to look at.
- **The FFmpeg column and the speedups** compare in-process Ragdoll library calls with whole FFmpeg command-line processes, which include process start-up, probing and file I/O, and, for `ffprobe`, JSON serialization of every packet. Those fixed costs dominate the short workloads, so the speedups mostly measure FFmpeg's start-up time. They are not codec-against-codec measurements and should not be quoted as such.
- **The second table** ("hardware PMU telemetry and battery efficiency") is mostly not measured:
  - instruction and cycle counts (and so IPC and GHz) print as `0` on Linux;
  - energy and power are estimates from a fixed model (CPU time, or cycles where available, times a constant), not readings from an energy counter, and the efficiency-mode constant is lower, which is where the `x vs P` savings come from;
  - the `E-Core%` column reads 100% whenever efficiency mode is selected unless the OS reports core residency;
  - `Mem(MiB)` is the peak resident memory of the whole `bench` process so far, so it only ever grows from row to row;
  - the FFmpeg row's version label is fixed text, not the version on your `PATH`.

For measurements you can rely on, time Ragdoll and FFmpeg the same way, in-process and single-threaded, as described in [Benchmarks](/docs/benchmarks/).
